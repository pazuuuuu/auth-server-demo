# SLO（サービスレベル目標）

> 版 v0.2（§7 のリスクを修正。計測は未実装）／2026-10-17
> 進め方は利用者判断で **案A＝まず docs で定義し、計測・アラートは後の段階で入れる**（2026-10-17）。

## 0. この文書の位置づけ

- このリポジトリの OIDC プロバイダについて、**何を測り（SLI）、どこまでを良しとし（SLO）、外れたら何を止めるか（エラーバジェットの運用ルール）** を決める。
- いまは**計測していない**。SLO の値はすべて**仮の初期値**で、計測を入れて 2〜4 週間の実績が取れたら見直す（§6）。
- 実装例のリポジトリなので、**SLA（利用者との契約）は結ばない**（§5）。

用語（Google SRE 本 4 章）：

| 用語 | 意味 | この文書での扱い |
|---|---|---|
| SLI | サービスの良し悪しを表す計測値。「良いイベント ÷ 有効なイベント」の比率で書く | §2 |
| SLO | SLI に対する目標値と期間 | §3 |
| SLA | 利用者との契約。未達時の補償がつく | §5（結ばない） |
| エラーバジェット | `1 − SLO`。期間中に失敗してよい量 | §4 |

## 1. 重要な利用者の行動（CUJ）

「止まると利用者（エンドユーザー・RP＝連携先アプリ）が困る行動」から選ぶ。測りやすさでは選ばない。

| ID | 行動 | 誰が困るか | 主なエンドポイント |
|---|---|---|---|
| `CUJ-1` | パスワードでログインする | エンドユーザー | `POST /login` |
| `CUJ-2` | パスキーでログインする | エンドユーザー | `POST /webauthn/authenticate/options` → `POST /login/webauthn` |
| `CUJ-3` | RP が認可コードを受け取る | RP・エンドユーザー | `GET /oauth2/authorize`（ログイン済み・同意済みのとき） |
| `CUJ-4` | RP がトークンを受け取る・更新する | RP | `POST /oauth2/token`（`authorization_code`・`refresh_token`） |
| `CUJ-5` | RP が設定と検証鍵を取得する | RP（ID トークンの検証） | `GET /.well-known/openid-configuration`・`GET /oauth2/jwks` |
| `CUJ-6` | パスワードを再設定する | エンドユーザー | `POST /forgot-password`・`POST /reset-password` |

`CUJ-4`・`CUJ-5` は RP の全ログインが依存するので、最も厳しくする。`CUJ-6` は頻度が低く、失敗しても別の手段（再試行・パスキー）があるので緩くする。

## 2. SLI の定義

### 2.1 共通の決めごと

- **比率で書く**：`良いイベント ÷ 有効なイベント`。
- **利用者の誤りはサービスの失敗に数えない**：パスワード違い（`/login?error` への 302）、期限切れの再設定トークン、`invalid_grant`・`invalid_client` などの 4xx は「サービスが正しく断った」ので**良いイベント**に含める。
  - ただし 4xx の急増（例：全 RP で `invalid_client`）は設定事故の兆候なので、SLO とは別に監視する。
- **有効なイベントから除く**もの：ヘルスチェック、明らかなボット・スキャン（未登録の `client_id`）、計画メンテナンス中の要求。
- **計測点**は、サーバーではなくロードバランサー（またはクライアント）に近いほうがよい（SRE Workbook「Implementing SLOs」）。いまは LB が無いので、計測を入れる段階ではアプリの HTTP メトリクスから始め、LB を置いたら移す。

### 2.2 SLI 一覧

| ID | CUJ | 種類 | 良いイベント | 有効なイベント |
|---|---|---|---|---|
| `SLI-1a` | CUJ-1 | 可用性 | 5xx 以外で応答した `POST /login` | `POST /login` 全件 |
| `SLI-1b` | CUJ-1 | レイテンシ | 1,000 ms 以内に応答した `POST /login` | 同上 |
| `SLI-2` | CUJ-2 | 可用性 | 5xx 以外で応答したパスキー認証の2要求 | パスキー認証の要求全件 |
| `SLI-3` | CUJ-3 | 可用性 | 5xx 以外で応答した `GET /oauth2/authorize` | 同エンドポイント全件 |
| `SLI-4a` | CUJ-4 | 可用性 | 5xx 以外で応答した `POST /oauth2/token` | 同エンドポイント全件 |
| `SLI-4b` | CUJ-4 | レイテンシ | 300 ms 以内に応答した `POST /oauth2/token` | 同上 |
| `SLI-5a` | CUJ-5 | 可用性 | 5xx 以外で応答した discovery・JWKS | 両エンドポイント全件 |
| `SLI-5b` | CUJ-5 | 正しさ | 発行した ID トークンの `kid` が、その時点の JWKS に含まれていた割合 | 発行した ID トークン全件 |
| `SLI-6` | CUJ-6 | 可用性 | 5xx 以外で応答した再設定の2要求 | 再設定の要求全件 |

- `SLI-1b` のしきい値が `SLI-4b` より緩いのは、パスワードのハッシュ照合（`PasswordEncoder`）がわざと遅いため。
- `SLI-5b` は「RP が ID トークンを検証できるか」を表す。v0.1 では JWK を起動ごとに作り直しており、**再起動するとそれまでの ID トークンを検証できなくなった**（v0.2 で修正・§7）。いまは鍵のローテーションで旧鍵の公開鍵を JWKS から外すのが早すぎたときに消費する。

### 2.3 SLI にしないもの

- CPU・メモリ・DB コネクション数などの内部指標：原因の調査には使うが、利用者の体験を直接表さないので SLI にしない。
- **セキュリティ上の不変条件**（PKCE なしの要求を断る、使用済みのリフレッシュトークンを断る、CSRF 不一致で状態を変えない 等）：「99.9% 守れればよい」ものではなく、**常に守る**。SLO・エラーバジェットの対象にせず、規約テスト・テスト（`docs/harness.md`）で見張る。

## 3. SLO（仮の初期値）

期間はすべて **28 日のローリング**。

| SLO | SLI | 目標 | 28 日のエラーバジェット | 理由 |
|---|---|---|---|---|
| `SLO-1a` | SLI-1a | 99.9% | 0.1%（停止なら約 40 分） | ログインできないと全 RP が使えない |
| `SLO-1b` | SLI-1b | 99% | 1% | ハッシュ照合ぶんの余裕を見る |
| `SLO-2` | SLI-2 | 99.5% | 0.5% | パスワードという代替手段がある |
| `SLO-3` | SLI-3 | 99.9% | 0.1% | ログインと同じ重さ |
| `SLO-4a` | SLI-4a | 99.95% | 0.05%（停止なら約 20 分） | RP のサーバー間通信。失敗するとログイン全体が失敗する |
| `SLO-4b` | SLI-4b | 99% | 1% | |
| `SLO-5a` | SLI-5a | 99.95% | 0.05% | RP は鍵をキャッシュするが、更新時に取れないと検証が止まる |
| `SLO-5b` | SLI-5b | 99.9% | 0.1% | 鍵のローテーションの手順ミスで消費する（§7） |
| `SLO-6` | SLI-6 | 99% | 1% | 頻度が低く、急ぎでない |

値の決め方：

- **100% は目標にしない**。非現実的で、変更（デプロイ）ができなくなる（SRE 本 4 章）。
- 実績が無いので、上の値は CUJ の重さから置いた仮の値。実績が取れたら**出発点として**使ってよいが、実績をそのまま目標に固定しない（SRE Workbook「Implementing SLOs」・SRE 本 4 章）。
- 依存先（PostgreSQL＝Supabase）の可用性より高い値は実現しにくい。見直しのときに Supabase 側の公表値と比べる。

## 4. エラーバジェットの運用ルール

| 状態 | 判定 | やること |
|---|---|---|
| 余裕あり | 28 日の消費が 50% 未満 | 通常どおり。機能追加の PR を進めてよい |
| 注意 | 50% 以上 100% 未満 | 新しい機能 PR は1件ずつ。原因になった変更を調べ、PR 説明に SLO への影響を書く |
| 枯渇 | 100% 以上 | **信頼性の修正・セキュリティ修正（`fix:`・`security:`）以外のマージを止める**。消費の原因をふり返りに残す |

- セキュリティ修正は、バジェットの状態にかかわらず止めない。
- 1件の障害でバジェットの 20% 以上を使ったら、ふり返り（何が起きたか・なぜ検知が遅れたか・再発防止）を書く。
- 凍結の例外はリポジトリの持ち主が判断し、判断の理由を PR に残す。

### 4.1 アラート（計測を入れる段階の方針）

SRE Workbook「Alerting on SLOs」の複数窓・バーンレート方式に合わせる（下の値は同書の 99.9%・30 日の推奨例。28 日でもほぼ同じ）：

| 重さ | 長い窓 | 短い窓 | バーンレート | 消費するバジェット |
|---|---|---|---|---|
| 呼び出し | 1 時間 | 5 分 | 14.4 | 2% |
| 呼び出し | 6 時間 | 30 分 | 6 | 5% |
| チケット | 3 日 | 6 時間 | 1 | 10% |

## 5. SLA

- 実装例のリポジトリなので、**SLA は結ばない**。
- このコードを元にサービスを提供して SLA を結ぶ場合は、**SLA を SLO より緩くする**（例：SLO 99.95% に対して SLA 99.9%）。社内の目標を厳しくしておくと、契約違反の前に手を打てる（SRE 本 4 章）。測定方法・除外条件（計画メンテナンス、利用者側の誤り）・補償を契約に書く。

## 6. 計測と見直し（次の段階）

いまは計測していない。次の段階（案B）で入れる候補：

1. Spring Boot Actuator と Micrometer を入れ、`http.server.requests` を `uri`・`status`・`outcome` で集計する（レイテンシはヒストグラムを有効にする）。
2. SLO の定義を機械で読める形（例：OpenSLO・Sloth）にし、§4.1 のアラートを生成する。
3. `SLI-5b` は、発行時の `kid` と JWKS の突き合わせが要るので、独自のメトリクスにする。

見直し：

- 計測を入れて 2〜4 週間の実績が取れたら、§3 の値を見直して版を上げる。
- その後は四半期ごと、または CUJ・アーキテクチャが変わったとき。
- 見直したら、この文書の版と、判断が変わった理由を残す（`CLAUDE.md`「唯一の正」）。

## 7. いまの実装で SLO を消費しやすいところ

v0.1 で挙げたリスクと、v0.2 での直し方（方針は利用者判断・2026-10-17）。

| 箇所 | v0.1 の動き | 影響する SLO | v0.2 での直し方 |
|---|---|---|---|
| JWK（`SigningKeys`・`AuthorizationServerConfig#signingKeys`） | 起動ごとに RSA 鍵を作り直す | `SLO-5b`：再起動の前に発行した ID トークンを RP が検証できなくなる | **環境変数 `JWT_SIGNING_KEY`（PEM）から読む**。`kid` は鍵のサムプリント（RFC 7638）＝同じ鍵なら再起動しても同じ。鍵が無ければ起動しない（`dev` とテストだけ起動ごとの鍵を許す）。ローテーション中は旧鍵の公開鍵を `JWT_PREVIOUS_PUBLIC_KEYS` で JWKS に並べ、署名は今の鍵だけで行う |
| パスキーの資格情報（`SecurityConfig#userCredentialRepository`） | メモリ上（`MapUserCredentialRepository`・利用者の user handle も） | `SLO-2`：再起動で登録済みのパスキーが消え、ログインできなくなる | **DB の表 `user_credentials`・`user_entities` に置く**。Spring Security 6.4 には JDBC 版が無いので自作（`JdbcUserCredentialRepository`・`JdbcPublicKeyCredentialUserEntityRepository`）。表の形は 6.5 の標準に合わせ、Boot 3.5 に上げたら置き換えられるようにした |
| パスワード再設定トークン（`PasswordResetTokenService`） | メモリ上 | `SLO-6`：再起動で送った再設定リンクが使えなくなる | **DB の表 `password_reset_token` に、トークンの SHA-256 ハッシュだけを置く**。有効なリンクは利用者ごとに1本（新しく送ると前のリンクは使えない）。使うときは期限内の行を消せた要求だけがパスワードを変える（同時に2回使っても1回だけ） |
| 複数台構成 | 上の3つはプロセスごとに持つ | 台数を増やすと、要求が別の台に行ったときに失敗する | 上の3つが DB と環境変数に移ったので、同じ鍵と DB を共有すれば複数台で動く |

根拠になるテスト：`SigningKeysTest`・`JwksEndpointTest`・`PasskeyRepositoriesTest`・`PasswordResetFlowTest`。

## 8. DORA メトリクスとの関係

`docs/harness.md` の CI・記録（`harness-events`）と組み合わせると、DORA の指標を SLO で判定できる。

| DORA 指標 | SLO との関係 |
|---|---|
| デプロイ頻度 | §4 のルールで、バジェットが残っていれば攻め、枯渇したら止める |
| 変更失敗率 | 「デプロイ後に SLI が SLO を割った」を失敗の判定基準にできる |
| デプロイ失敗時の復旧時間 | 「SLI が SLO の水準に戻るまで」を復旧と定義できる |
| 手戻り率 | §4 の `fix:` によるマージが増えると上がる |

DORA は信頼性（可用性・レイテンシ等の目標をどれだけ満たしているか）を、デリバリーの5指標とは別の「運用パフォーマンス」として扱っている（dora.dev「DORA metrics history」）。
